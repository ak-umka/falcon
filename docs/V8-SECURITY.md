# Безопасность v8: ключи, их смена, ответы на ревью

## Секреты и их назначение

| Секрет | Где | Для чего | Что затрагивает смена |
|---|---|---|---|
| `PROVIDER_ENCRYPTION_KEY` | Sites secret | AES-GCM шифрование ключей пользователей (DeepSeek, HeyGen, OpenAI, Google, ElevenLabs, Shotstack, Telegram, YouTube) в D1 | все сохранённые подключения перестают расшифровываться |
| `SIGNING_KEY` (новый в v8) | Sites secret | HMAC-подписи: ссылки на медиа для внешнего рендера (6 ч), OAuth state YouTube (10 мин) | только выданные и ещё не истёкшие ссылки и незавершённые подключения YouTube |
| `PRODUCTION_RUNNER_TOKEN` | Sites secret + `.env` runner | доступ runner к `/api/internal/*` | runner получает 403, пока токен не обновлён с обеих сторон |
| `YOUTUBE_CLIENT_ID` / `YOUTUBE_CLIENT_SECRET` | Sites secret | OAuth-клиент Google | новые подключения и обновление токенов YouTube |
| `PIXABAY_API_KEY` | `.env` runner | поиск фото | только фото в новых роликах |

Требования к `SIGNING_KEY`: не короче 32 символов и **не равен** `PROVIDER_ENCRYPTION_KEY` — иначе студия отказывается выдавать подписи (503). Создание: `openssl rand -hex 32`.

Ключи пользователей (DeepSeek, Telegram, YouTube и др.) хранятся только зашифрованными, в браузер не возвращаются; runner их не получает.

## Смена ключей

**`SIGNING_KEY`** — можно менять в любой момент, данные не теряются.
1. `openssl rand -hex 32` → новый secret `SIGNING_KEY` в Sites → развернуть версию.
2. Последствия: внешние ссылки на медиа, выданные Shotstack до смены, перестанут открываться (обычно сборка уже завершена; незавершённую — запустить снова); незавершённое подключение YouTube — нажать «Подключить» ещё раз.

**`PRODUCTION_RUNNER_TOKEN`** — короткий простой runner.
1. `openssl rand -hex 32`.
2. Обновить secret в Sites → развернуть версию.
3. Обновить `PRODUCTION_RUNNER_TOKEN` в `.env` runner → `docker compose up -d`.
4. Проверить статус «Runner активен». Аренды заданий (5–10 мин) защищают от двойной обработки во время переключения.

**`PROVIDER_ENCRYPTION_KEY`** — менять только при компрометации; ротации «на месте» нет.
- Вариант А (простой): задать новый ключ, затем каждый пользователь заново подключает свои сервисы в «AI-подключения» и «Новостной радар». Старые зашифрованные записи можно удалить: `DELETE FROM media_connections; DELETE FROM ai_connections; DELETE FROM connections;` — только после резервной копии D1.
- Вариант Б (без переподключения): разовый скрипт-миграция в Worker, который расшифровывает каждую запись старым ключом и шифрует новым (оба ключа заданы на время миграции). В v8 не реализован; требует отдельной задачи и проверки на копии базы.
- Шифротекст привязан к `owner_id` и провайдеру (AAD), поэтому перенос на другой сайт с другими ID владельцев тоже требует переподключения.

**`YOUTUBE_CLIENT_SECRET`** — в Google Cloud → Credentials → клиент → «Add secret», сохранить новый в Sites, развернуть, затем удалить старый в Google. Сохранённые refresh-токены продолжают работать; если клиент удалён целиком — пользователи подключают YouTube заново.

**Ключи пользователей** (DeepSeek, Telegram-бот, HeyGen и др.) — пользователь перевыпускает ключ у сервиса (для бота — `/revoke` у @BotFather) и заново подключает его в студии; старый ключ у сервиса отзывается.

**`PIXABAY_API_KEY`** — перевыпустить в кабинете Pixabay, обновить `.env` runner, `docker compose up -d`.

## Ответы на ревью от 21.10.2026

1. **Отдельный ключ для подписей render-grants** — сделано. `lib/render-grants.ts → signingSecret()` читает `SIGNING_KEY`, проверяет длину ≥ 32 и отличие от `PROVIDER_ENCRYPTION_KEY`. Тот же ключ использует OAuth state YouTube (`lib/channels.ts`) — до правки он тоже был производным от ключа шифрования. Тест: `tests/render-grants.test.mjs` («render grants require a separate signing key»).
2. **Атрибуты cookie входа ChatGPT** — cookie входа выставляет платформа Sites, код студии cookie авторизации не создаёт (только читает доверенные заголовки `oai-authenticated-user-*`). Проверено на опубликованном сайте 21.10.2026: `GET /signin-with-chatgpt` ставит cookie входа с `HttpOnly; Secure; SameSite=Lax; Max-Age=600`. Сессионную cookie после `/callback` выставляет та же платформа; её атрибуты владелец может подтвердить в DevTools после входа. Локальная тестовая cookie (`pnpm dev`) — `HttpOnly; SameSite=Lax`, без `Secure`, потому что работает по http://127.0.0.1 и только с локальных адресов. Единственный `document.cookie` в коде — неиспользуемый компонент `components/ui/sidebar.tsx` (состояние боковой панели, не авторизация).
3. **POST для `/api/youtube/connect`** — сделано. Маршрут принимает только POST; `identity()` для не-GET запросов требует `Origin` своего сайта. Проверено локально: GET → 405, POST с чужим Origin → 403, POST без Origin → 403, POST со своего сайта → ссылка Google. `/api/youtube/callback` остаётся GET (так требует Google) и защищён подписанным state, привязанным к владельцу и сроку 10 минут: чужой код подключения к другому пользователю не применится.
4. **Смена ключей** — этот документ.

Дополнительно проверено 21.10.2026: 51 тест проходит; `pnpm run build` (pnpm 11.25.0, Node 24.19.0) завершается успешно, миграция `0007` входит в сборку.
